# 運用の設計（正本）

『とびだせ どうぶつの森』と『ハッピーホームデザイナー』の解析と、その結果を使う製品づくりを、どう進めるかの決まりです。

## 0. この文書について

- 運用の決まりの正本です。利用者が了承した設計書（2026-10-14 の第 15 版）を元に、2026-11-03 までの決定を入れて書き直しました。
- 人が読む文書です。エージェントに毎回は読ませません。エージェントへの指示（`CLAUDE.md`・`AGENTS.md`・スキル・ワーカーの定義・依頼文の雛形）は、この文書に合わせて短く書きます。
- 指示や道具と食い違ったら、この文書を正しいとして直します。今わかっている食い違いは 17 節にあります。
- 変更は利用者の承認を得て、PR で行います。
- ワーカーにも効く決まりは、記憶に置かずこの文書に書きます。記憶に置くのは、利用者の好みと、司令塔だけに関係する事です。

## 1. 方針

1. **判断・設計・調査は司令塔が行い、手順が決まった作業はワーカーが行う。** 判断や設計はモデルの質に大きく左右されますが、やる事がはっきりした作業は安価なモデルでも失敗しにくいからです。
2. **合格した物だけが正本に入る。** ワーカーはコピーを変更して PR にし、司令塔が読んで取り入れるかを決めます。
3. **決まった操作は道具に任せる。** AI の手順の抜けや取り違えを防ぎ、利用枠も使いません。
4. **利用枠の消費を抑える。** 消費は「文脈の大きさ × 要求の回数」でほぼ決まるので、この 2 つを小さくします（8 節）。

## 2. 構成

```
ac3ds-workspace/   作業場。司令塔はここで起動する
├─ docs/           この文書
├─ skills/         司令塔のスキルの本体（.claude/skills へ配置する）
├─ templates/      依頼文の雛形
├─ scripts/        orch.py など司令塔の道具
├─ workspace.toml  リポジトリの一覧
├─ workers.toml    ワーカーの設定
├─ ac3ds-re/       解析リポジトリ（ゲームの事実だけを書く）
├─ gohan/ など     派生リポジトリ（解析の結果を使う製品）
└─ _local/         Git に入れない物（ROM、IDB、書き出し、作業ツリー、証拠、ログ）
```

- 対象のビルドは ACNL 日本版の無印＋更新（`acnl_jpn_v15`）と HHD v1.1（`hhd_jpn_v11`）です。
- 各リポジトリは単独でも使えます。解析の規則は `ac3ds-re/AGENTS.md` とそのスキルだけでそろいます。
- リポジトリは public で、ライセンスは MIT です。ROM・IDB・疑似 C・個人の情報は Git に入れません。監査（コミット前と CI）と、`orch.py` が GitHub へ書く前の検査で止めます。

| 役 | 担当 | 読む | 判断する | 書く |
|---|---|---|---|---|
| 利用者 | — | — | 目的、承認が要る操作、提供元の使い分け、格付け | 実機の確認 |
| 司令塔 | Opus 5.5（effort は利用者が設定） | 全部 | 調査の結論、設計、ワーカーの結果、再試行、取り込み | 設計書、Issue、`orch.py` の操作 |

| 設計書 | ○ | 依頼された時だけ案を書く |

| 記録の中身（`kb.py new` で作る）、topics | — | ○ |

| 正本の IDB への取り込み | ○（`orch.py`） | — |
| コミット、PR、取り込み、push | ○（`orch.py`） | — |

## 4. 作業の流れ

1. **受付（司令塔）**: 目的と完了条件を確かめます。
2. **調査と設計（司令塔）**: 既存の資料を引き、必要な原典を読み、やる事を決めます（5.1・5.2）。
3. **依頼（司令塔）**: `orch.py capacity` を確かめ、`orch.py issue`・`dispatch`・`claude`（または `codex`）で依頼します。
4. **作業（ワーカー）**: 自分の作業ツリーと IDB のコピーの中だけで作業します。
5. **機械の検証（道具）**: `orch.py save`・`stamp`・`verify` が保存・監査・ビルド・試験を行います。落ちたら司令塔は読まず、結果をワーカーへ戻します。
6. **判断（司令塔）**: 差分と成果物を読んで決めます（5.3）。
7. **確定（道具）**: `orch.py accept`（打ち切りは `reject`）。
8. **報告（司令塔）**: 完了したこと、判断してほしいこと、実機確認の依頼を利用者に伝えます。

1 タスク＝1 Issue＝1 ブランチ＋1 PR です。試行ごとにコミットして push し、取り込まなかった物も PR に残ります。

## 5. 司令塔の仕事

### 5.1 調査

- 読む前に既存の物を引きます。`kb.py search`・`addr`、topics、`_local/evidence`、設計書、旧版のソースと文書です。語を替えて引きます（例: 「最適化」だけでなく「共通化」も）。
- 大きなファイルは丸ごと読まず、関数や節の単位で読みます。独立に読める物は 1 回の要求にまとめます。
- 調べた結論は、設計書か topics に残します。同じ調査を二度しないためで、次のセッションへの引き継ぎにもなります。
- ワーカーに調査を頼んだ時は、結果を材料として扱い、終わったら司令塔が原典を読みに行って判断します。
- 判断を含まない材料集め（棚卸しの表、大きさの測定など）は、まず道具で、次にワーカーで行います。

### 5.2 設計

- 依頼文には、変更する関数、触らない物、確かめ方を書きます。ワーカーが探し回らずに済むようにするためです。
- 大きな作業は 8 節の大きさに分けます。

### 5.3 判断

判断の材料は、ワーカーの完了報告ではなく、成果物と差分です。

- **読む物**: 差分の全部、機械の検証の結果、試験の中身（何を確かめているか）、関係する設計書の節。見た目の作業は、全場面の絵を拡大して見ます。解析は、記録の本文と根拠の関数を書き出しで読みます。
- **格付けで変える深さ**:

| ワーカーの格付け | 差分に加えて確かめる物 |
|---|---|
| C・?（Haiku など） | 根拠を一次証拠で全部確かめる。解析の記録は A 以上の確認が要る |
| A（Sonnet など） | 結論に効く根拠を一次証拠で確かめる |
| S（Opus） | 抜き取りで確かめる |

- **採点表**: 各項目 0〜1 で採点します。全項目が 0.6 以上で合格です（基準は 2026-10-15 の較正で決めました）。点数と判定の理由を PR に残します。
  - 解析: 根拠と結論の一致、根拠の独立性、既存の知見との整合、確度の妥当性、名前・型の妥当性。
  - 派生: 完了条件の達成、設計書との整合、既存の知見との整合、試験の妥当性、決まりの順守。
- **疑わしい部分**: 合否と別に書き出します。合格でも、解析の記録で疑わしい部分があれば、取り込む前に「反証条件・未確認点」へ移すか確度を下げさせます。
- **深い検証に回す物**: 多くの関数から使われる名前・型、HIGH への昇格、上位の格付けの記録の訂正、topics の更新、ゲーム API ヘッダーに入る物、司令塔の重要な結論。関数の境界や型は Ghidra の独立の出力でも確かめます。枠が足りない時は、利用者の指示で他の提供元の格付け A に代えられます。その時は「Opus 未確認」の Issue を残します。

### 5.4 再試行と訂正

- 再試行は 3 回までです。指摘を伝えて直させ、次に effort を上げ、次にモデルを上げます。それでも駄目なら利用者に報告します。
- 文脈が大きい時や間が空いた時は、同じセッションでなく新しいセッションで頼みます（8 節）。
- 既存の記録と食い違う結論は、新しい記録に `supersedes:` を書いて提案させます。古い記録は書き換えません。一次証拠が強い方を採り、格付けは証拠が同等の時の決め手にします。決着しなければ実機確認の Issue を作ります。

## 6. ワーカーの仕事

- **範囲**: 依頼文の作業ツリーと IDB のコピーの中だけです。`git`・`gh` は使いません。正本の IDB は開きません。
- **依頼文**: タスクに固有の事だけを書きます。目的と完了条件、作業の場所、読む物、事前に引いた知見です。設計書は、該当の節を貼ります。リポジトリの `AGENTS.md` と重なる定型は書きません。派生リポジトリの `AGENTS.md` に書けない事（解析の資料の場所と、`kb.py` で既存の知見を引くこと）は、依頼文の定型に残します。
- **報告**: 最後の返答で次の項目だけを返します。`orch.py` が `.task/report.md` に保存します。
  - 未確認点
  - 迷った判断
  - 依頼の範囲外の変更
  - 使ったゲームの事実（ゲームに触る作業だけ。番地、根拠の関数、確度）
- 変更したファイル、試験の結果、記録の一覧は道具が作るので、報告に書きません。
- 派生のワーカーは新しいゲームの事実を「記録すべき事実」として報告に足します。司令塔が解析の Issue にします。
- 解析のワーカーは、該当する時だけ、訂正の提案、統合・重複の提案、新しいタグの提案を足します。

### 作業中にゲームの調査が要る時

依頼の後で、ゲームの実装を調べる必要が分かることがあります。大きさで分けます。

| 場合 | 目安 | ワーカーがすること |
|---|---|---|
| 小さな確認 | 既存の記録と書き出しで、10 関数までを読めば分かる | 自分で調べて続ける。IDB には触らない |
| 止まる | 書き出しで答えが出ない、実機の確認が要る、依頼文の前提が違った、新しいフックや書き込み先を決める必要がある、10 関数を超える | 問いを具体的に書いて止まる。実装は進めない |
| 名前や型が無い | symbols に無い関数や型を使いたい | 止まる。司令塔が解析の Issue にし、symbols に入ってから使う |

- 止まった時は司令塔が引き取ります。自分で調べるか、解析の Issue にして結論を出し、結論を記録か設計書に残してから続きを頼みます。
- 大きな調査は実装と分けます。調査の依頼で結果を短いファイルに書かせ、実装は新しいセッションで始めます。
- 使ったゲームの事実は、司令塔が 5.3 節の深さで一次証拠と照らします。
- 10 関数は仮の目安です。実際の作業で測って直します。

## 7. モデルの選び方

- **Codex と Claude のどちらを優先するかは決めません。** 週の枠などの状況を見て、利用者がその都度指示します。指示が無い間は、直前の指示を続けます。
- 格付けは `ac3ds-re/meta/models.toml` にあり、利用者が管理します。S は Opus 5.5、A は Sonnet 5.5・gpt-6.1-sol・gpt-6-astra、B は opus-5・gpt-sol-5.6・gpt-6-sol、C は Haiku 5.5・gpt-6-luna、? は gpt-6・unknown です。
- `hard` は A 以上、`normal` は B 以上、`easy` は誰でも担当できます。
- Codex は砂場を使わず全権限で起動する（2026-11-09 の利用者の方針。砂場では MSYS が止まり make が通らない）。

| 作業 | Claude の場合 | effort の既定 |
|---|---|---|
| 単純作業（機械的な変換、取り込み、小さな修正） | Haiku 5.5 | medium |
| 実装、解析、ゲームの実装に触る作業 | Sonnet 5.5 | medium |
| デザインなど、利用者が指定した物、Sonnet でも無理な物 | Opus 5.5 | high |

ゲームの実装に触る作業を Haiku に出さないのは、格付け C の結果は司令塔が根拠を全部確かめる必要があり、一番高い所の読む量が増えるからです。番地の表を写すだけのような単純作業は別です。

Haiku の担当を「手順が明確で文脈が 10 万トークンに収まる物」に広げるかは、測ってから提案します。

## 8. 費用の設計

### 8.1 消費の数え方

Claude Code は要求のたびに文脈全体を送ります。だから、一度文脈に入った物は、以後の要求すべてで読み直されます。測った結果（ワーカー 19 ログと司令塔 1 セッション、定価で計算した相対値）は次のとおりです。

| 分かった事 | 数値 |
|---|---|
| 入力側（キャッシュの読みと書き）が大半 | Haiku #76 で読みが 84%、司令塔で読みと書きが約 80% |
| Haiku は文脈が 10 万トークンを超えると単価が 5 倍 | 全ての Haiku のセッションが 26〜66 万に達した |
| 読み込みが文脈を太らせる | 道具の結果の 68.4% が Read |
| effort が高いと出力も文脈に積もる | Haiku xhigh の 1 要求の出力は Sonnet の約 2 倍 |
| 司令塔が新しく読む物は高い | 1 時間のキャッシュの書きは読み直しの 40 倍 |
| 間を空けた再開は全部を書き直す | 21 万トークンの再開で約 $0.84（Sonnet） |
| 依頼文の定型の割合は小さい | 読みの 1% 前後 |

利用枠の本当の重みは公開された資料で確かめられていません。実際の内訳は `/usage` で見られます。

### 8.2 決まり

| # | 決まり | 実現の方法 |
|---|---|---|
| C1 | ワーカーの文脈は 10 万トークンまで。司令塔が 1 依頼をその大きさに分ける | `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000` |
| C2 | ワーカーは大きなファイルを丸ごと読まない。設計書は該当の節を依頼文に貼る | `CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS=8000` |
| C3 | effort の既定を下げる | 7 節 |
| C4 | ワーカーの道具を絞る（最初の文脈が 24,034 → 13,706 トークン。実測） | `--tools Read,Edit,Write,Grep,Glob,Bash,PowerShell`。IDA を使う作業は IDA の道具を足す |
| C5 | 司令塔のセッションは段ごとに切る。目安は 20 万トークン。1 時間以上空くなら再開しない。5 時間枠が変わる時も切り替える。結論は設計書に書いて次へ渡す | 利用者が新しいセッションを開く |
| C6 | 直しは、文脈が 5 万トークンを超える時や間が空いた時は、新しいセッションで頼む。差分と指摘だけを渡す | `orch.py claude` |
| C7 | ビルドと試験は LLM なしで先に走らせ、通った物だけ、差分と結果を 1 つのファイルにして司令塔が読む | `orch.py verify` |
| C8 | 報告は 6 節の項目だけ。依頼文の定型を消す（派生の `AGENTS.md` に書けない事は残す） | 雛形とワーカーの定義 |
| C9 | 依頼ごとの費用・要求数・最大の文脈を測る。暴走は予算で止める（初期値は 1 依頼 $5。値は測って決める） | `orch.py stats`、`--max-budget-usd` |

C1・C2 は細部が落ちたり読む回数が増えたりする恐れがあります。最初の 3 件で測り、効かなければ値を変えるか戻します。

既定のシステムプロンプトの置き換えは採りません（差が 3,700 トークンほどで、挙動が変わる恐れの方が大きいためです）。

## 9. 利用枠と中断

- 依頼の直前に毎回 `orch.py capacity` を確かめます。5 時間枠が 80% 以上、または推奨が 0 なら新しい依頼を出しません。
- 動いているワーカーは、見張りが 80% で止めます。続きは `--resume` か新しいセッションで頼みます。司令塔自身は見張られないので、自分で確かめます。
- 80% を超えても、もう出たワーカーの結果の判断はしてかまいません。
- 中断は `orch.py wrapup` です。全ての試行を保存し、引き継ぎメモを書きます。引き継ぎメモには次の 1 手だけを書き、決まりは書きません。
- ワーカーの並列は最大 3 つで、互いに独立したタスクだけです。旧記録の作業は利用枠の 3 割までにします。

## 10. 知識（記録と topics）

- **二層**: 先に `topics/`（今わかっている事）を読み、根拠が要る時に `findings/`（1 件 1 ファイル）を読みます。記録は `kb.py new` で作ります。モデル名は `by: auto` と書かせ、`orch.py stamp` が実際の名前で上書きします。
- **確度**: HIGH は静的解析と実測、MEDIUM は互いに独立した複数の静的根拠、LOW は仮説です。LOW では名前を付けず、コメントだけ入れます。
- **格付け**: C と ? の記録だけを根拠にしません。「?」は再解析が済むまで C と同じです。
- **再解析**: 使う時に、使う記録だけ行います。全件の再解析は行いません。
- **消化**: 自動では行いません。カテゴリを使う作業の前にだけ行い、topics の更新は深い検証に回します。
- **事前確認**: 解析の前に `kb.py addr`・`search` を引きます。解析は UI 周りから進めます。

## 11. IDB・symbols・書き出し

- 正本の IDB には、合格した symbols の差分だけを取り込みます。作業はタスクごとのコピーで行います。正本は、照合済みの code.bin から作り、symbols を取り込んだ物です。
- symbols は IDA と Ghidra で共有します。
- **全関数の書き出し**は `_local/builds/<ビルド>/export/` にあり、IDB を開かずに関数を読むための物です。名前や型の取り込みの後、解析の作業の前に作り直します（`orch.py export`）。
- **復元の試験**（空の IDB に symbols を取り込んで正本と比べる。`ac3ds-re/tools/sync/restore_test.py`）で、IDB を symbols から作り直せることを確かめます。

## 12. Git と公開

- ワーカーはコミットしません。`orch.py` が試行ごとにコミットして push し、初回に draft の PR を作ります。取り込みはマージコミットで、ブランチは自動で消します。
- `.task/` は作業ブランチだけで使い、取り込みの前に消します。
- 誤りの戻し方: 合格させた物が誤っていたら `git revert`。不合格にした物が正しかったら、閉じた PR からブランチを戻します。IDB の取り込みが誤っていたら、バックアップか symbols から作り直します。
- コミットの作者は GitHub の noreply アドレスです。

### 12.1 WebChat（外部の解析ワーカー）

WebChat は ChatGPT の Web 画面で、利用者が手で操作します。台帳（`_local/state`）には載らず、ID の台帳も使えません。運用の手順書は `_local/orchestrator/webchat/project-prompt.md`（Git の外）です。

- **ラベル**: `webchat`（WebChat が担当する Issue）と `作業中`（ワーカーが取って作業している Issue）の 2 つです。WebChat は Issue を取る時に `作業中` を付けます。`dispatch` は、どちらかが付いた Issue を断ります。`dispatch` が通ると `作業中` を付け、`accept` と `reject` の後に外します。
- **依頼**: `orch.py issue --webchat ...`（解析リポジトリだけ）で、ラベル `webchat` と WebChat への指示を付けた Issue を作ります。
- **受け箱**: WebChat は記録の下書きを `inbox/webchat/<Issue 番号>/<連番>.md` に置き、ブランチ `webchat/<Issue 番号>` から PR を出します。PR 本文の先頭は `Issue #N` です。PR の差分が受け箱の外に及ぶ物は取り込みません。
- **取り込み**: `orch.py webchat verify <PR>`（ブランチを作業ツリーに取り出し、main に追いつかせ、機械の検証を走らせる）、`webchat accept <PR> --scores ... --read <ファイル>`（検証の後に `kb.py intake --issue N --by gpt-6-sol` で ID を振り、結果を push して PR にコメントし、取り込む。Issue は閉じる）、`webchat reject <PR> --reason ...`（PR を閉じる。Issue は開いたまま）です。採点表は解析の物を使います。
- **直しの依頼**: 利用者が、開いている WebChat の PR に直しを頼むことがあります。WebChat は同じブランチに push し、PR に「利用者の指示」と直した報告をコメントします（手順書 9 節）。直しのコメントの後に、利用者から「終わった」と伝わるまで `webchat verify` に進みません。取り込み済みの PR は直さず、新しい Issue と `supersedes:` つきの下書きで訂正します。打ち切った PR は、同じ Issue でやり直します。
- **利用者の実機での観察**: 利用者がその場で実機を確かめ、結果を WebChat に伝えることがあります。WebChat は、それを下書きの根拠の「利用者の実機での観察」に書き、確度は MEDIUM までにします（手順書 10 節）。WebChat は証拠のファイルを残せないためです。HIGH に上げるかは取り込みの時に司令塔が決めます。上げる時は、利用者に証拠（画像・値）を `_local/evidence/<Issue 番号>/` に置いてもらい、記録にパスと SHA256 を書きます。
- **始める時（1 回だけ）**: `orch.py setup-github ac3ds-re` でラベルを作り、利用者が手順書を ChatGPT のプロジェクトに貼ります（2026-11-09 に済み）。

### 12.2 作業場（ac3ds-workspace）の変更

`orch.py` の依頼先に作業場はありません。道具の変更は、道具のワーカー（Agent ツールの `tooling`）に作業場の作業ツリーで頼みます。

- **作業ツリー**: `workspace.local.toml` の `git`（`C:/Program Files/Git/cmd/git.exe`）で `_local/worktrees/ws-<名前>` に作り、`workspace.local.toml` を写して、`ac3ds-re` をジャンクションで張ります。PATH の先頭の `git` は devkitPro の msys2 の物で、これで作ると `.git` が msys 形式のパスになり Git Bash から使えません。`workspace.local.toml` が無いと道具と試験もその git を使い、`scripts/tests` の stamp・accept の試験が `audit` の CRLF で落ちます。
- **採点**: 司令塔が差分を読み、作業ツリーで `scripts/tests` を走らせます（全体で 20 分ほど。裏で走らせる）。
- **取り込み**: main は保護され、監査の CI（`audit`）が必須です。push → `gh pr create` → `gh pr checks <n> --watch` → `gh api -X PUT repos/yak9909/ac3ds-workspace/pulls/<n>/merge -f merge_method=merge`（`gh pr merge --delete-branch` はこの環境で止まる）→ 本体で `git pull --ff-only` し、作業ツリーとブランチを消します。
- **ラベルを足した時**: `orch.py setup-github <リポジトリ>`（リポジトリは位置引数）。リポジトリの設定・ラベル・main の保護を書き直し、何度走らせても同じ結果になります。

## 13. 派生リポジトリ

## 15. 指示の書き方と見直し

- 指示は最小限にします。書くのは、この案件に固有の約束、直感に反する規則、破ると損害が大きいのに仕組みで防げない事です。モデルが既定でする事や、仕組みが保証する事は書きません。
- 1 つの規則は 1 か所に書きます。
- 削りすぎにも注意します。実際に問題になった事（暗算の誤りなど）は短くても書きます。
- 問題が起きたら、すぐに書き足さず、利用者に会話で提案します。原因がモデルの能力なら再試行の段階を上げ、仕組みで防げるならそちらを先に提案します。承認されたら PR で反映し、新しいセッションから適用します。
