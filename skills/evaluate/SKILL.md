# 採点

## 読む物

判断の材料は、報告でなく成果物と差分。読んだ物の一覧をファイルに書き、`orch.py accept --read <ファイル>` に渡す。

- 共通: 差分の全部、`orch.py stamp`・`verify` の結果、`.task/report.md`。
- 解析: 新しい記録の本文（結論・根拠・反証条件）、根拠に挙げた関数の書き出し（`_local/builds/<ビルド>/export/`）の該当部分、`kb.py search`・`addr` で引いた既存の記録と symbols。
- 派生: 関係する設計書の節、`kb.py` で引いた既存の知見と旧版の該当部分、試験の中身（何を確かめているか）。ワーカーが報告した「使ったゲームの事実」も、下の深さで一次証拠と照らす。
- 見た目（デザイン・描画・画面の絵）: 全場面の絵を、拡大した切り抜き（6〜12 倍）で1枚ずつ見る。
- 正本の IDB は開かない。

## 格付けで変える深さ

| ワーカーの格付け | 差分に加えて確かめる物 |
|---|---|
| C・?（Haiku など） | 根拠を一次証拠で全部確かめる。解析の記録は A 以上の確認が要る |
| A（Sonnet など） | 結論に効く根拠を一次証拠で確かめる |
| S（Opus） | 抜き取りで確かめる |

## 採点表: 解析（各項目 0〜1 と、全体の合否）

| 項目 | 見ること |
|---|---|
| 根拠と結論の一致 | 根拠から結論が言えるか。飛躍は無いか |
| 根拠の独立性 | 互いに独立した根拠があるか（疑似C の言い換え2つは独立ではない） |
| 既存の知見との整合 | 既存の記録・symbols と矛盾しないか。矛盾するなら訂正の提案になっているか |
| 確度の妥当性 | 確度が根拠に見合っているか |
| 名前・型の妥当性 | `ac3ds-re/docs/naming.md` に合い、役割を正しく表しているか |

## 採点表: 派生（各項目 0〜1 と、全体の合否）

| 項目 | 見ること |
|---|---|
| 完了条件の達成 | Issue の完了条件を、差分と出力（絵・試験の結果）で確かめて満たしているか |
| 設計書との整合 | 派生リポジトリの設計書と、作業場の設計書の決定事項に合っているか |
| 既存の知見との整合 | ゲームの事実の使い方が、記録・symbols・旧版の知見と矛盾しないか |
| 試験の妥当性 | 試験が変更の要点を確かめているか。通るだけの試験になっていないか |
| 決まりの順守 | 派生リポジトリの AGENTS.md を守っているか |

- 合格の基準は `workers.toml` の `[evaluation].pass_min`（どの項目もこれ以上）。
- 結論のうち根拠が弱い部分（疑わしい部分）を、合否と別に書き出す。
- 合格でも解析の記録に疑わしい部分があれば、取り込む前にワーカーへ戻し、その部分を「反証条件・未確認点」へ移すか確度を下げさせる。
- 点数・疑わしい部分・判定の理由を、PR のコメントに残す。

## 深い検証に回す物

- 多くの関数から使われる名前・型、HIGH への昇格、上位の格付けの記録の訂正、消化（topics の更新）、ゲーム API ヘッダーに入る物、司令塔自身の重要な結論。
- 検証役は `python scripts/orch.py review <Issue> --effort <effort> --message-file <依頼文>` で起動する（effort は難易度 hard なら high、それ以外は medium）。依頼文には、記録・作業ツリー・IDB コピーの場所を書く。報告は `_local/orchestrator/review/` に残るので、`orch.py accept --reviewed` に渡す。続きは `--resume` を足す。
- 依頼文には次も書く: 関数は全関数の書き出し（`_local/builds/<ビルド>/export/`）で読む。関数の境界・型など重要な点は、Ghidra の独立の出力（ac3ds-re の `python tools/sync/ghidra/run.py dump --build <ビルド> --target <番地> --create`）でも確かめる。
- 利用枠が足りなければ、利用者の指示で他の提供元の格付け A に代えられる。その時は「Opus 未確認」の Issue を残す。
