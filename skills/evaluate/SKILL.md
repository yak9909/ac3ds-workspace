# 採点

## 読む物

オーケストラは解析・実装をしないが、採点に要る物は自分で読む。報告だけで採点しない。読んだ物の一覧をファイルに書き、`orch.py accept --read <ファイル>` に渡す。

- 共通: `orch.py stamp` が出す要約（変更したファイル・新しい記録とその確度・symbols の差分・検査の結果）と、ワーカーの `.task/report.md`。
- 解析: 新しい記録の本文（結論・根拠・反証条件）、根拠に挙げた関数の書き出し（`_local/builds/<ビルド>/export/`）の該当部分、`kb.py search`・`addr` で引いた既存の記録と symbols。
- 派生: 変更の差分、関係する設計書の節、`kb.py` で引いた既存の知見と旧版の該当部分、試験の中身（何を確かめているか）。
- 見た目（デザイン・描画・画面の絵）: 全場面の絵を、拡大した切り抜き（6〜12 倍）で1枚ずつ見る。報告の「直した」を、絵で確かめる。
- IDB を開いての解析や、一次証拠を使った新しい結論づくりはしない。それが要るなら深い検証に回す。

## 採点表: 解析（各項目 0〜1 と、全体の合否）

| 項目 | 見ること |
|---|---|
| 根拠と結論の一致 | 根拠から結論が言えるか。飛躍は無いか |
| 根拠の独立性 | 互いに独立した根拠があるか（疑似C の言い換え2つは独立ではない） |
| 既存の知見との整合 | 既存の記録・symbols と矛盾しないか。矛盾するなら訂正の提案になっているか |
| 確度の妥当性 | 確度が根拠に見合っているか |
| 名前・型の妥当性 | `ac3ds-re/docs/naming.md` に合い、役割を正しく表しているか |

## 採点表: 派生（各項目 0〜1 と、全体の合否）

| 項目 | 見ること |
|---|---|
| 完了条件の達成 | Issue の完了条件を、差分と出力（絵・試験の結果）で確かめて満たしているか |
| 設計書との整合 | 派生リポジトリの設計書と、作業場の設計書の決定事項に合っているか |
| 既存の知見との整合 | ゲームの事実の使い方が、記録・symbols・旧版の知見と矛盾しないか |
| 試験の妥当性 | 試験が変更の要点を確かめているか。通るだけの試験になっていないか |
| 決まりの順守 | 派生リポジトリの AGENTS.md（層の向き・ゲーム由来の物を入れない・解析の ID やパスを書かない）を守っているか |

- 合格の基準は `workers.toml` の `[evaluation].pass_min`（どの項目もこれ以上）。
- 結論のうち根拠が弱い部分（疑わしい部分）を、合否と別に書き出す。
- 合格でも疑わしい部分があれば、取り込む前にワーカーへ戻し、その部分を「反証条件・未確認点」へ移すか確度を下げさせる（較正で、誤りの記録の多くは合格のまま疑わしい部分として現れた）。
- 点数・疑わしい部分・判定の理由を、PR のコメントに残す。

## 深い検証に回す物

- 多くの関数から使われる名前・型、HIGH への昇格、上位の格付けの記録の訂正、消化（topics の更新）、ゲーム API ヘッダーに入る物。
- `.claude/agents/reviewer` を起動する（effort は難易度 hard なら high、それ以外は medium）。依頼文には、記録・作業ツリー・IDB コピーの場所を書く。
- 依頼文には次も書く: 関数は全関数の書き出し（`_local/builds/<ビルド>/export/`）で読む。関数の境界・型など重要な点は、Ghidra の独立の出力（ac3ds-re の `python tools/sync/ghidra/run.py dump --build <ビルド> --target <番地> --create`）でも確かめる（IDA の解析と独立に確かめるため）。
- 利用枠が足りなければ gpt-6.1-sol に代えて、「Opus 未確認」の Issue を残す。
