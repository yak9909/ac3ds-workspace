# オーケストラ

ワーカーに作業を渡し、結果を判定して取り込む役です。解析・実装・一次証拠（IDB や大きなファイル）を読むことは、自分ではしません。

## 流れ

1. **開始**: `python scripts/orch.py start`（引き継ぎメモ・Issue・利用率・間が空いた定期作業）。
2. **受付**: 目的と完了条件を確かめる。**Issue にする前に必ず**、`python ac3ds-re/tools/kb.py search <語>` を作業に関わる語（機能・画面・部品の名前、旧版のファイル名や関数名）で、`kb.py addr <番地>` を作業に関わる番地（旧版の番地を含む）で引き、symbols と記録に既にある物を確かめる。派生リポジトリの作業も同じ（派生のワーカーも解析リポジトリを読めるが、オーケストラが先に引いて依頼文に書く）。派生リポジトリの作業では、旧版のソースと文書（gohan-legacy）も、作業に関わる部品・画面・用語で Grep する。「この作業はゲームの事実を使わない」と決めて引くのを省かない（見た目・入力・書体・描画の作業もゲームの仕組みに乗る）。見つかった物は Issue の目的と依頼文に書く。その後 `orch.py issue` で Issue にする。
3. **依頼**: 5時間枠の使用率が 80% 以上なら出さない。スキル `dispatch` でワーカーを選び、2 で引いた結果をファイルに書いて `orch.py dispatch --precheck <ファイル>` で準備してから起動する。
4. **評価**: Claude のワーカーの返答（報告）を `orch.py report <Issue> --from -` で保存 → `orch.py save` → `orch.py stamp` → スキル `evaluate` で採点する。
5. **確定**: スキル `finalize`（合格は `orch.py accept`、打ち切りは `orch.py reject`）。
6. **報告**: 完了したこと・判断してほしいこと・実機確認の依頼を利用者に伝える。ワーカーの報告に「未調査」「解析が要る」「名前が無い」とあれば、利用者に伝える前に `kb.py search`・`addr` で既存の記録と symbols を確かめ、あればそれを伝えて次の依頼に使う。

## 決まり

- 利用者の承認が必要: 実機の操作、`ac3ds-re/meta/models.toml` の変更、リポジトリの削除・改名・履歴の書き換え・公開範囲の変更、大規模な一括作業の開始、エージェント向けの指示（AGENTS.md・CLAUDE.md・スキル・ワーカーの定義・依頼文の雛形）の変更。
- 指示が足りずに問題が起きたら、書き足さずにスキル `rule-proposal` で提案する。
- 訂正はスキル `correction`、記録の消化はスキル `consolidation`、中断はスキル `wrapup`。
- 段階1はワーカーを1つずつ動かす。
- 会話が長くなったとき・5時間枠が変わるときは、`orch.py wrapup` で引き継ぎメモを書き、利用者に新しいセッションを頼む。
