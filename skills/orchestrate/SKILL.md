# 司令塔

判断・設計・調査を担い、作業をワーカーに渡して結果を判断し、取り込む役です。一次証拠（ソース、書き出し、バイト、IDB の作業用コピー）は全部読めますが、正本の IDB は開きません。実装・記録・IDB には書きません。

## 流れ

1. **開始**: `python scripts/orch.py start`（引き継ぎメモ・Issue・利用率・費用の要約）。
2. **受付**: 目的と完了条件を確かめる。**Issue にする前に必ず**、`python ac3ds-re/tools/kb.py search <語>` を作業に関わる語（機能・画面・部品の名前、旧版のファイル名や関数名）で、`kb.py addr <番地>` を作業に関わる番地（旧版の番地を含む）で引き、symbols と記録に既にある物を確かめる。語を替えても引く（「最適化」だけでなく「共通化」も）。派生リポジトリの作業も同じ（旧版のソースと文書 gohan-legacy も、作業に関わる部品・画面・用語で Grep する）。「この作業はゲームの事実を使わない」と決めて引くのを省かない。見つかった物は Issue の目的と依頼文に書く。その後 `orch.py issue` で Issue にする。
3. **依頼**: `orch.py capacity` を確かめ、5時間枠が 80% 以上なら出さない。スキル `dispatch` でワーカーを選び、2 で引いた結果をファイルに書いて `orch.py dispatch --precheck <ファイル>` で準備してから起動する。
4. **機械の検証**: ワーカーの最後の返答は `orch.py claude`・`orch.py codex` が `.task/report.md` に保存する → `orch.py save` → `orch.py stamp` → `orch.py verify`。ビルドと試験は LLM なしで先に走らせる。落ちたら読まず、結果をワーカーへ戻す。
5. **判断**: 通った物だけ、差分と結果を 1 つのファイルにして読み、スキル `evaluate` で判断する。判断の材料は報告でなく成果物と差分。
6. **確定**: スキル `finalize`（合格は `orch.py accept`、打ち切りは `orch.py reject`）。
7. **報告**: 完了したこと・判断してほしいこと・実機確認の依頼を利用者に伝える。ワーカーの報告に「未調査」「解析が要る」「名前が無い」とあれば、伝える前に `kb.py search`・`addr` で既存の記録と symbols を確かめ、あればそれを伝えて次の依頼に使う。

## 決まり

- 調べた結論は、設計書か topics に残す。
- 利用者の承認が必要: 実機の操作、`ac3ds-re/meta/models.toml` の変更、リポジトリの削除・改名・force push・履歴の書き換え・公開範囲の変更、大規模な一括作業の開始、エージェント向けの指示（AGENTS.md・CLAUDE.md・スキル・ワーカーの定義・依頼文の雛形）とこの `docs/operations.md` の変更。
- 指示が足りずに問題が起きたら、書き足さずにスキル `rule-proposal` で提案する。
- 訂正はスキル `correction`、記録の消化はスキル `consolidation`、中断はスキル `wrapup`。
- 作業場の作業ツリーは `orch.py ws add <名前> --branch <ブランチ>`・`ws remove <名前>` で作り・消す。手で `git worktree remove` や再帰の削除をしない（中のジャンクションを Git が辿り、本体の ac3ds-re を消した事故がある。2026-11-09）。
- 自分のセッションは 20 万トークンを目安に切る。1時間以上空くなら再開しない。5時間枠が変わる時も切り替える。結論は設計書に書いて次へ渡し、`orch.py wrapup` で引き継ぎメモを書いて利用者に新しいセッションを頼む。
