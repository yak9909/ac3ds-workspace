# 依頼と再試行

## ワーカーの選び方

- 格付けは `ac3ds-re/meta/models.toml`。`hard` は A 以上、`normal` は B 以上、`easy` は誰でも担当できる。
- Codex と Claude のどちらを使うかは、利用者がその都度指示する。指示が無い間は直前の指示を続ける。

| 作業 | Claude の場合 | effort の既定 |
|---|---|---|
| 単純作業（機械的な変換、取り込み、小さな修正） | haiku-5.5 | medium |
| 実装、解析、ゲームの実装に触る作業 | sonnet-5.5 | medium |
| デザインなど利用者が指定した物、Sonnet でも無理な物 | opus-5.5 | high |

- ゲームの実装に触る作業は Sonnet 以上に出す（格付け C の結果は根拠を全部確かめる必要があるため）。番地の表を写すだけのような単純作業は別。
- Codex は `python scripts/orch.py codex <Issue>` で起動する。
- Claude のワーカーは `python scripts/orch.py claude <Issue>` で起動する。サブエージェント（Agent ツール）では起動しない。
  - PowerShell ツールの `run_in_background` で動かし、1 回だけ届く完了の知らせを待つ（Git Bash から起動すると `make` の環境変数が渡らない）。
  - 最後の返答は `.task/report.md` に自動で保存される。`--resume` の時は前の報告の後ろに足す。
  - 実行中のログは `_local/logs/claude_<リポジトリ>_<Issue>_<n>.jsonl`。5時間枠の実測を読み、上限に達したら止める（終了コード 3。続きは `--resume`）。
  - 手で止める時は、起動したバックグラウンドのシェルを止める。ワーカーが裏で起動した試験は残ることがあるので確かめる。
- 旧記録の作業（「?」の記録の再解析・消化）は、利用枠の3割までにする。

## 依頼文

- 雛形は `templates/dispatch.md`（派生リポジトリは `templates/dispatch-derived.md`）。`orch.py dispatch` が作る。
- タスクに固有の事だけを書く（目的・完了条件・作業ツリーと IDB コピーの場所・資料・事前確認の結果）。変更する関数、触らない物、確かめ方を書き、ワーカーが探し回らずに済むようにする。設計書は該当の節を貼る。リポジトリの `AGENTS.md` と重なる事は書かない。
- 大きなファイルは丸ごと読ませず、読む節や関数を指す。1 依頼は文脈 10 万トークンに収まる大きさに分ける。
- 事前確認の結果（`--precheck` のファイル）は省けない。引いた語・番地と、見つかった名前・記録 ID・格付け・要点を書く。何も無かったときは、引いた語と番地と「該当なし」を書く。派生リポジトリへの依頼では、記録 ID は依頼文にだけ書く。格付け ? や C の記録だけなら、使う前に確認の Issue を出すか、依頼文に「未確認の手がかり」と書く。

## 並べてよい条件

- 互いに独立したタスクだけ。同じアドレスや話題のタスクは同時に出さない。
- 並列は最大3つ。

## 再試行（3回まで）

1. 指摘と不足していた前提を伝えて直させる。
2. effort を上げる。
3. モデルを上げる（例: haiku-5.5 → sonnet-5.5、sonnet-5.5 → opus-5.5）。
4. それでも駄目なら利用者に報告する。

- 直しは、ワーカーの文脈が 5 万トークンを超える時や間が空いた時は、同じセッションでなく新しいセッションで頼む。差分と指摘だけを渡す（`orch.py claude <Issue> --message-file <ファイル>`）。それ以外は `orch.py claude <Issue> --resume --message-file <ファイル>`。
- 最初からやり直すときは、今の PR を理由付きで閉じ、新しいブランチと PR で始める（同じ Issue に結び付ける）。
- 大きな調査は実装と分ける。調査の依頼で結果を短いファイルに書かせ、実装は新しいセッションで始める。
